# План реализации Dubai Deal Sniper

## Принятая стратегия

Продукт строится на Firebase и Google Cloud и развивается двумя пользовательскими этапами:

1. **Telegram-бот** — первый MVP для проверки сбора, расчётов и полезности сигналов.
2. **Telegram Mini App** — следующий интерфейс после пилота, использующий тот же Cloud Run API и Firestore.

Backend работает независимо от Telegram. Аукционы и недвижимость не входят ни в один этап.

## Целевая Google Cloud архитектура

```text
Cloud Scheduler
→ Cloud Run Job: collector
→ Cloud Storage: сырой снимок
→ Cloud Firestore: метаданные и версия
→ Cloud Tasks: идемпотентная обработка
→ Cloud Run Service: pricing, risk, API, Telegram webhook
→ Firestore: решение и действия пользователя

после пилота:
Firebase Hosting: TMA
→ Firebase Authentication
→ тот же Cloud Run Service
```

Используемые управляемые сервисы:

- Cloud Run Service и Cloud Run Jobs;
- Cloud Scheduler и Cloud Tasks;
- Cloud Firestore Native mode;
- Cloud Storage;
- Vertex AI Gemini через `google-genai`;
- Secret Manager;
- Cloud Logging и Cloud Monitoring;
- Firebase Hosting и Firebase Authentication для TMA;
- Artifact Registry и Cloud Build либо GitHub Actions для доставки образов;
- BigQuery только после появления достаточной истории для аналитики.

В первом MVP не требуются VPS, PostgreSQL, Redis и Celery.

## Этап 0. Бизнес-параметры

Зафиксировать целевые марки, модели, годы, бюджет, минимальную прибыль, минимальный ROI, максимальный срок продажи, допустимость import/non-GCC и стоп-факторы риска.

**Критерий готовности:** каждое правило имеет название, единицу измерения, значение и объяснение.

## Этап 1. Google Cloud foundation

Создать или выбрать Firebase/Google Cloud project и единый регион. Включить необходимые API, подготовить отдельные service accounts с минимальными IAM-ролями, Artifact Registry, Firestore, Storage bucket, Tasks queue, Scheduler и Secret Manager.

Инфраструктуру описать через Terraform или эквивалентный Infrastructure as Code. Service account JSON нельзя хранить в репозитории или контейнере; локальная разработка использует Application Default Credentials.

**Критерий готовности:** тестовый Cloud Run Service и Job разворачиваются воспроизводимо, обращаются к Firestore и Storage под отдельными service accounts, а секрет читается только из Secret Manager.

## Этап 2. Firestore-модель и идемпотентность

Создать коллекции:

- `sources`;
- `listings` и подколлекции `snapshots`;
- `vehicles`;
- `decisions`;
- `users`, `settings` и `favorites`;
- `notifications`;
- `outcomes`.

Сырые HTML/JSON сохранять в Cloud Storage, а в Firestore — ссылку, контрольную сумму и индексируемые поля. `listing_id`, `content_hash`, task name и notification ID формировать детерминированно. Согласованные изменения выполнять транзакцией или batched write.

Перейти с `google.generativeai` на `google-genai`, заменить изменяемые значения по умолчанию Pydantic на `default_factory`. Конфигурации индексов Firestore и Security Rules хранить в репозитории.

**Критерий готовности:** повторный импорт одинакового объявления не создаёт снимок или Cloud Task; снижение цены создаёт ровно одну новую версию.

## Этап 3. Реестр источников и первый Cloud Run Job

Первым подключается Dubizzle после проверки разрешённого способа доступа. Cloud Scheduler запускает Cloud Run Job каждые 5–15 минут. Job сохраняет сырой снимок, обновляет Firestore и создаёт Cloud Task только для новой версии.

Mock-источник включается только через `ENABLE_MOCK_SOURCES=true`. Ошибка источника не подменяется тестовыми данными.

**Критерий готовности:** несколько дней стабильного запуска по расписанию; в Cloud Monitoring видны успешность, длительность, число новых версий и ошибки схемы.

## Этап 4. Обработка через Cloud Tasks

Cloud Task вызывает закрытый endpoint Cloud Run с OIDC-аутентификацией. Обработчик проверяет идемпотентность, нормализует объявление и изменяет явное состояние обработки.

Настроить отдельные очереди либо маршруты для обработки объявлений и Telegram-доставки, ограничения скорости, retry policy и dead-letter/операционный разбор окончательных ошибок.

**Критерий готовности:** повтор одной задачи не создаёт повторное решение, а временная ошибка автоматически повторяется.

## Этап 5. Нормализация и matching

Нормализовать марку, модель, поколение, год, комплектацию, двигатель, коробку, GCC/import specification, пробег, продавца, эмират и признаки повреждений.

Для Firestore хранить денормализованные индексируемые поля и `comparison_key`. Сначала применяются словари и правила; Vertex AI используется только для оставшегося неструктурированного текста. Для каждого значения сохраняются происхождение и confidence.

**Критерий готовности:** контрольная выборка корректно нормализуется по признакам, необходимым для поиска аналогов.

## Этап 6. Comparable Price Engine

Выбирать уникальные аналоги по `comparison_key`, модели, поколению, году, specification, комплектации и диапазону пробега. Разделять private, dealer, certified retail и C2B цены, учитывать свежесть и удалять выбросы.

Нужные composite indexes Firestore добавлять декларативно. Список аналогов и коэффициенты сохранять вместе с решением. BigQuery не используется для online-решения первого MVP.

**Критерий готовности:** каждую оценку можно воспроизвести по сохранённым данным Firestore.

## Этап 7. Расходы, риски и Decision Engine

Детерминированно рассчитывать полную себестоимость, `max_purchase_price_aed`, ожидаемую прибыль, ROI, confidence и действие `contact`, `watch`, `inspect` или `reject`.

Vertex AI не выполняет финансовую арифметику. Недостаток аналогов, неизвестный VIN, повреждение шасси, признаки затопления и неполные данные сохраняются как явные risk flags.

**Критерий готовности:** одинаковые входные документы всегда дают одинаковое финансовое решение без вызова Gemini.

## Этап 8. Cloud Run API и Telegram-бот

Cloud Run Service на Python 3.11 и FastAPI предоставляет Telegram webhook, обработчики Cloud Tasks и Application API. Бот отправляет цену продавца, максимальную цену покупки, рынок, расходы, прибыль, ROI, confidence, риски и ссылку.

Минимальные действия: открыть объявление, сохранить, отметить контакт, осмотр или отказ. Telegram token хранится в Secret Manager. Повтор доставки выполняется Cloud Tasks и не запускает повторный анализ.

**Критерий готовности:** webhook защищён секретом, доступ ограничен разрешёнными Telegram user ID, потерянные сообщения повторяются без дублей, действия сохраняются в Firestore.

## Этап 9. Пилот

Проверить 100–300 объявлений первого источника. Для лучших сигналов фиксировать ручную оценку, контакт, осмотр, прогноз и фактические расходы. Контролировать стоимость Cloud Run, Firestore, Tasks, Storage и Vertex AI.

**Критерий готовности:** измерена ошибка цены и ремонта, понятны причины ложных сигналов и подтверждена приемлемая стоимость одного обработанного объявления.

## Этап 10. Расширение источников

Подключать DubiCars, YallaMotor и остальные источники отдельными Cloud Run Jobs после access audit. После второго классифайда реализовать межсайтовое объединение по VIN, телефону, фотографиям и устойчивому отпечатку.

**Критерий готовности:** новый источник увеличивает число уникальных аналогов или полезных лидов без неконтролируемых дублей.

## Этап 11. Telegram Mini App

Разместить TMA на Firebase Hosting. `/api/**` проксируется в Cloud Run. Backend проверяет подпись Telegram `initData`, создаёт Firebase custom token, а frontend входит через Firebase Authentication.

Экраны TMA:

- лента возможностей;
- фильтры и настройки;
- карточка автомобиля;
- история цены и аналоги;
- избранное;
- результаты осмотров и сделок;
- статистика прибыли и ROI.

Security Rules не должны разрешать клиенту читать или изменять данные другого пользователя. Финансовые расчёты и сбор остаются только на backend.

**Критерий готовности:** TMA использует существующий API; закрытие TMA не влияет на сбор, расчёт и Telegram-уведомления.

## Этап 12. Outcome loop и аналитика

Сохранять фактические покупку, ремонт, продажу и срок экспозиции. После накопления истории выгружать события в BigQuery для анализа точности, сегментов и калибровки коэффициентов. Firestore остаётся оперативной базой.

## Правила выполнения каждого этапа

После каждого этапа обязательны автоматические тесты, проверка идемпотентности, IAM, индексов и правил Firestore, отсутствие повторных вызовов Vertex AI для неизменившихся объявлений и обновление `docs/STEPS.md` и `AI_CONTEXT.md`.
