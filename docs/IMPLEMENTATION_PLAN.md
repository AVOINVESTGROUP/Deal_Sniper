# План реализации Dubai Deal Sniper

Статус документа: новая редакция ожидает проверки и утверждения владельцем; код следующих релизов до утверждения не изменяется.

## 1. Цель MVP

Создать Telegram-бота, который регулярно получает объявления о продаже автомобилей с фиксированной ценой, сохраняет историю изменений, сравнивает автомобиль с актуальными аналогами и отправляет пользователю объяснимое решение:

- `CONTACT` — связаться с продавцом;
- `WATCH` — наблюдать за ценой;
- `INSPECT` — требуется проверка автомобиля;
- `REJECT` — предложение не соответствует заданным параметрам.

Для каждого решения бот показывает цену объявления, рыночный диапазон, максимальную цену покупки, расходы, ожидаемую прибыль, ROI, риски, уверенность и использованные аналоги.

Первый пользовательский интерфейс — обычный Telegram-бот. TMA создаётся только после рабочего пилота и использует тот же backend API.

## 2. Границы проекта

В MVP входят только автомобили с фиксированной ценой в ОАЭ.

Не входят:

- недвижимость;
- аукционы, ставки, таймеры и отслеживание торгов;
- автоматическая покупка автомобиля;
- автоматическая отправка сообщений продавцам;
- прогноз цены без подтверждающих рыночных данных;
- TMA до завершения пилота Telegram-бота.

Для внешнего источника учитываются только технические параметры интеграции: формат данных, авторизация, лимиты, частота обновления, стабильность схемы, мониторинг и стоимость обработки.

## 3. Подтверждённое текущее состояние

На 24.07.2026 существуют три разные точки состояния, которые нельзя называть одним baseline:

| Контур | Фактическое состояние |
|---|---|
| default-ветка `main` | legacy: `DubizzleMockScraper`, SQLite, `GEMINI_API_KEY`, LLM-оценка рынка и бесконечный локальный цикл |
| draft PR #1 / рабочая ветка | новая реализация: 17 коммитов относительно `main`, 54 изменённых файла, более 6 000 добавленных строк; CI проходит, но критические дефекты целостности и доступа ещё не устранены |
| Google Cloud production | развёрнут образ из рабочей ветки, а не из слитой и воспроизводимой default-ветки; фактический код production необходимо связать с commit SHA и image digest |

Следовательно, ни `main`, ни draft PR #1 пока не считаются утверждённым production-baseline. До новых продуктовых функций требуется стабилизация, разделение изменений на проверяемые PR и синхронизация `main` с реально развёрнутой версией.

| Область | Сейчас | Целевое состояние |
|---|---|---|
| Источник кода | production развёрнут из неслитой рабочей ветки; `main` остаётся legacy | защищённая `main` однозначно воспроизводит развёрнутый release |
| Запуск | четыре Cloud Run collector Jobs и Cloud Scheduler из draft-ветки | сохранить отдельные расписания и добавить управляемые content/publisher jobs |
| Данные | реальные DubiCars, CarSwitch, Cars24 и OpenSooq; raw и версии | расширять источники после контроля качества |
| Хранилище | Firestore и Cloud Storage; SQLite только локально | добавить поисковые запросы, публикации и audit log |
| Оценка | Engine `2.3.0` есть в draft-ветке, но расходы, риски, аналоги и provenance требуют исправления | экономически проверенный и версионированный расчёт с точным snapshot и market context |
| Каналы | публичный и Pro Telegram существуют, но старые публичные карточки полные | обязательные тизеры Free и полные карточки Pro |
| Пользователи | общий allowlist, watchlist Firestore не изолирован, административные команды доступны всем разрешённым пользователям | строгая изоляция данных и отдельные роли user/admin |
| Управление | Telegram-команды и Google Cloud Console | защищённая панель Firebase Hosting/Auth |
| Контент | публикации только по найденным сделкам | market pulse, price drops, обзоры и опросы по проверенным данным |
| WhatsApp | отсутствует | официальный Business API для opt-in получателей; Channel — только при появлении официального API |
| Проверки | unit, Ruff, mypy, CI и production smoke tests | добавить integration/E2E для новых каналов и панели |

Рабочая ветка является аварийно развёрнутым кандидатом baseline, но не утверждённым источником production-кода. Сначала выполняются релизы стабилизации `0.11A–0.11D`; только после их приёмки начинаются продуктовые релизы `0.12+`.

## 4. Принципы реализации

1. Одинаковые входные данные всегда дают одинаковое финансовое решение.
2. LLM не определяет рыночную цену, стоимость ремонта, прибыль, ROI или итоговое действие.
3. Неизменившаяся версия объявления не обрабатывается повторно и не вызывает Vertex AI.
4. Ошибка источника не подменяется mock-данными.
5. Сырые данные сохраняются до нормализации; каждое производное значение содержит provenance.
6. Backend не зависит от Telegram. Бот и будущая TMA являются клиентами Application API.
7. Каждый этап заканчивается работающим вертикальным результатом и автоматической проверкой.
8. Новые источники подключаются адаптерами, не меняющими расчётное ядро.
9. Решение всегда рассчитывается по точному `listing_id + content_hash`; подмена переданной версии последним snapshot запрещена.
10. Пользовательские данные всегда фильтруются по владельцу на уровне запроса и проверяются integration-тестами.
11. Временная ошибка внешнего сервиса приводит к контролируемому retry, а постоянная невалидность данных — к карантину.
12. Для внешней доставки не заявляется недостижимое «ровно один раз»: используется outbox, детерминированная идентичность, состояние неоднозначной доставки и запрет слепого повтора.
13. `main`, release image digest и фактически развёрнутая Cloud Run revision должны однозначно соответствовать друг другу.

## 5. Целевая схема

```text
Cloud Scheduler
    -> Cloud Run Job: collector-{source}
    -> Cloud Storage: raw snapshot
    -> Firestore: listing + snapshot metadata
    -> Cloud Tasks: process-listing
    -> Cloud Run API/worker
       -> normalize
       -> entity resolution
       -> comparable pricing
       -> cost and risk
       -> decision
       -> optional Vertex AI enrichment
       -> Firestore: decision
       -> Cloud Tasks: Telegram delivery
       -> Telegram Bot API

Telegram webhook -> Cloud Run API -> Firestore
Firebase Hosting: Admin -> Firebase Auth -> Cloud Run Admin API
PublicationEvent -> Telegram Free adapter
                 -> Telegram Pro adapter
                 -> Telegram personal adapter
                 -> WhatsApp Business adapter (только после настройки)
TMA после пилота -> Firebase Hosting/Auth -> тот же Cloud Run API
```

- выбрать один способ работы с Telegram; удалить неиспользуемую библиотеку;
- добавить `httpx` прямой зависимостью, если остаются прямые HTTP-вызовы;
- добавить `pyproject.toml`, Ruff, mypy и pytest;

- для каждого fixture вручную зафиксировать ожидаемый рыночный диапазон, расходы, риски и решение;
- отделить доменный пакет от Firestore, Telegram и Vertex AI.

Критерий приёмки:

### Релиз 0.4. Один реальный источник и история цены

Первым подключается один источник с достаточным количеством объявлений с фиксированной ценой. Mock scraper остаётся только в тестах.

Задачи:

- определить интерфейс `SourceAdapter` и структуру `source_registry`;
- реализовать реальный адаптер первого источника;
- добавить timeouts, rate limiting, retry с exponential backoff и circuit breaker;
- сохранять исходный HTML/JSON в Cloud Storage;
- формировать стабильный `listing_id` из source ID либо канонического набора признаков;
- формировать `content_hash` значимых полей;
- хранить каждый изменившийся snapshot в Firestore;
- добавить состояния `active`, `changed`, `removed`, `stale`;
- реализовать события `new_listing`, `price_changed`, `listing_removed`;
- исключить создание новой версии и дальнейшую обработку неизменившегося объявления;
- добавить технические метрики: fetched, parsed, changed, failed, duration и last_success_at.

Критерий приёмки:

- collector стабильно работает не менее 72 часов в dev;
- повтор одного запуска не создаёт дубли;
- изменение цены создаёт новый snapshot и событие;
- ошибка источника видна в метриках и не создаёт тестовые объявления;
- raw snapshot позволяет повторно выполнить parsing без обращения к источнику.

Критерий приёмки:

### Релиз 0.6. Детерминированный Comparable Price Engine

Задачи:

- выбирать аналоги по модели, поколению, году, trim, specification и пробегу;
- разделять private, dealer, certified retail и C2B цены;
- учитывать свежесть объявления;
- удалять дубли и выбросы;
- рассчитывать `low`, `median`, `high`, размер выборки и `coverage_score`;
- хранить список использованных и отклонённых аналогов с причиной;
- запретить расчёт сделки при недостаточном покрытии рынка;
- добавить backtesting на fixture-наборе.

Критерий приёмки:

- одинаковые входы дают побитно стабильный результат;
- изменение одного параметра приводит к объяснимому изменению оценки;
- результат содержит все аналоги и поправки;
- при недостатке данных возвращается `insufficient_data`, а не выдуманная цена.

### Релиз 0.7. Cost, Risk и Decision Engines

Задачи:

- рассчитать проверку, ремонт, подготовку, хранение, стоимость капитала, расходы на продажу и резерв риска;
- поддержать точечные значения и диапазоны расходов;
- определить hard stop flags и предупреждения;
- рассчитывать консервативную цену перепродажи;
- рассчитывать максимальную цену покупки, прибыль и ROI;
- вернуть `CONTACT`, `WATCH`, `INSPECT`, `REJECT` или `INSUFFICIENT_DATA`;
- версионировать правила и конфигурацию решения;
- добавить regression tests для всех fixture-сценариев.

Основные формулы:

```text
conservative_resale_price = market_low - liquidity_discount
total_non_purchase_cost = inspection + repair + preparation + holding + selling + risk_reserve
max_purchase_price = conservative_resale_price - total_non_purchase_cost - target_profit
expected_profit = conservative_resale_price - asking_price - total_non_purchase_cost
roi_percent = expected_profit / (asking_price + total_non_purchase_cost) * 100
```

Критерий приёмки:

- арифметика и округление покрыты unit-тестами;
- правила не зависят от LLM;
- решение объясняет каждый вычет и stop flag;
- отсутствие обязательных данных снижает confidence либо останавливает решение.

### Релиз 0.9. Vertex AI enrichment

Vertex AI подключается через `google-genai` только после готового финансового решения.

Разрешённые задачи:

- извлечение признаков из неструктурированного описания;
- выделение текстовых risk flags;
- краткое объяснение уже рассчитанного решения.

Задачи:

- использовать service account и Vertex AI без production API-ключа;
- валидировать ответ по схеме;
- ограничить timeout, число попыток, токены и стоимость;
- кэшировать результат по `content_hash + prompt_version + schema_version + model_id`;
- вызывать модель только для нового или изменившегося snapshot;
- продолжать обработку при недоступности Vertex AI;
- собирать метрики количества вызовов, задержки, ошибок и стоимости.

Критерий приёмки:

- отключение Vertex AI не меняет числа и итоговое финансовое решение;
- повтор snapshot не вызывает модель;
- невалидный ответ отклоняется и не попадает в доменную модель;
- установлен проверяемый месячный лимит расходов.

### Релиз 0.10. Расширение источников

Задачи:

- подключать источники по одному через `SourceAdapter`;
- начать с двух дополнительных классифайдов с фиксированной ценой;
- затем подключить C2B-ориентиры, certified retail, данные расходов и проверки состояния;
- для каждого источника определить `source_role`, `price_type`, `seller_type` и `source_confidence`;
- выполнять cross-source entity resolution до расчёта рынка;
- добавить contract tests на сохранённых raw snapshots;
- реализовать мониторинг изменения схемы каждого адаптера.

Критерий приёмки:

- сбой одного адаптера не останавливает остальные;
- цены разных типов не смешиваются в одну среднюю;
- повторные публикации одного автомобиля не искажают рынок;
- для каждого источника видны свежесть, покрытие и процент ошибок.

### Релиз 0.11. Пилот и калибровка

Объём пилота: не менее 100–300 обработанных объявлений и ручная проверка всех отправленных кандидатов.

Измерять:

- precision уведомлений `CONTACT/INSPECT`;
- долю `INSUFFICIENT_DATA`;
- ошибку рыночной оценки на доступном ground truth;
- долю дублей после entity resolution;
- задержку от появления объявления до уведомления;
- число повторных уведомлений;
- долю ошибок collector и parsing;
- стоимость обработки объявления и месячную стоимость облака;
- переходы `уведомление -> контакт -> осмотр -> покупка -> продажа`.

Критерий приёмки:

- пороги KPI утверждены до начала пилота;
- каждый ложный сигнал относится к конкретной причине;
- коэффициенты изменяются только версионированной конфигурацией;
- решение о переходе к TMA принимается по итогам пилота, а не по готовности интерфейса.

### Релиз 0.11A. Целостность версий, доступ и доставка

Статус: обязательный блокирующий релиз до слияния новой реализации и до любых функций монетизации.

Задачи:

- добавить `get_snapshot(listing_id, content_hash)` во все Repository и рассчитывать решение только по точной версии;
- отклонять processing task, если указанный snapshot отсутствует или его hash не совпадает;
- исправить `user_watchlist(user_id)` и все пользовательские запросы так, чтобы фильтрация владельца выполнялась в Firestore/SQLite, а не после общего scan;
- разделить `TELEGRAM_ADMIN_USER_IDS` и обычных пользователей; централизовать authorization guard для каждой команды;
- оставить управление источниками, ручной scan и системный status только администраторам;
- заменить read-then-batch обновление current listing транзакцией либо update precondition с проверкой монотонности `observed_at`;
- добавить out-of-order тест: версия A не может перезаписать current pointer после версии B;
- классифицировать detail verification на `verified`, `permanent_invalid` и `temporary_error`;
- для timeout, HTTP 429 и 5xx возвращать retriable ответ Cloud Tasks, для постоянной невалидности — карантин без retry;
- заменить безусловный ранний claim Telegram `update_id` состояниями `processing/completed/failed` с lease и безопасным повтором;
- расширить delivery identity полями `engine_version`, `template_version`, `format` и target;
- ввести outbox-состояния `pending/sending/sent/failed/unknown`, lease и audit поля;
- не обещать строгую exactly-once доставку через Telegram: при неоднозначном сетевом результате переводить событие в `unknown` и не выполнять слепой повтор.

Критерий приёмки:

- задача версии A никогда не создаёт решение из snapshot B;
- два пользователя не могут прочитать действия и watchlist друг друга;
- обычный пользователь получает `403` на все административные операции;
- конкурентные и out-of-order записи сохраняют правильный current snapshot;
- 429/5xx detail page приводит к retry, постоянный `Price on request` — к карантину;
- delivery ID различается для новой версии Engine и шаблона;
- integration-тесты покрывают Firestore emulator, Cloud Tasks retry и Telegram failure windows.

## 7. Сквозные требования

### Надёжность

- все сетевые операции имеют timeout;
- повторяются только временные ошибки;
- задачи идемпотентны;
- предусмотрены dead-letter состояния;
- graceful shutdown обязателен для Service и Jobs;
- недоступность одного источника не останавливает pipeline.

### Данные

- Firestore хранит оперативные и индексируемые данные;
- Cloud Storage хранит raw snapshots;
- SQLite не используется в production;
- URL не является единственным идентификатором;
- история цены и состояния объявления не перезаписывается;
- все timestamps хранятся в UTC.

### Секреты и доступ

- секреты не находятся в Git, Docker image или обычных переменных CI;
- production использует Secret Manager и service accounts;
- IAM выдаётся отдельно API, collectors, Tasks и CI;
- Telegram MVP ограничен allowlist пользователей;
- логи не содержат токены, телефоны и полный текст секретов.

### Тестирование

- unit tests — модели, формулы, нормализация и правила;
- contract tests — адаптеры на сохранённых raw snapshots;
- integration tests — Firestore emulator и API;
- end-to-end smoke test — collector fixture -> decision -> тестовая Telegram-доставка;
- regression tests — контрольный датасет;
- load test — обработка пачки объявлений и очередь уведомлений.

### Наблюдаемость и стоимость

- единый correlation ID проходит через collector, task, decision и notification;
- логи структурированы;
- определены метрики свежести, ошибок, задержки, дублей и стоимости;
- настроены алерты на отсутствие успешного сбора, рост ошибок и backlog очереди;
- настроены бюджеты и лимиты Vertex AI.

## 8. Порядок выполнения ближайших работ

Переход к полной реализации подтверждён владельцем проекта. Релизы выполняются в следующем порядке:

1. получить от владельца правки и явное утверждение этой редакции плана;
2. выполнить `0.11A`: точные версии, изоляция пользователей, роли, retry и outbox;
3. выполнить `0.11B`: достоверность цен, аналогов, рисков и финансовой модели;
4. выполнить `0.11C`: lifecycle, масштабирование, конфигурация, IaC и воспроизводимая сборка;
5. выполнить `0.11D`: заменить draft PR #1 проверяемой серией PR, слить baseline в `main` и развернуть тот же image digest;
6. выпустить разделение `Free teaser / Pro full card`;
7. выпустить пользовательский `/find` и подписки на новые совпадения;
8. выпустить административную панель на Firebase Hosting/Auth;
9. выпустить информационный модуль в режиме предварительного согласования;
10. перейти к автоматическим информационным публикациям после ручной проверки шаблонов;
11. подключить официальный WhatsApp Business adapter после предоставления Meta-реквизитов;
12. провести контрольный запуск монетизации и только затем возвращаться к TMA.

Каждый релиз выполняется отдельным pull request либо небольшой серией pull request. Следующий релиз не начинается, пока не выполнены критерии приёмки предыдущего или письменно не зафиксировано исключение.
