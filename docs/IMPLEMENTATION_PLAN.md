Статус документа: новая редакция ожидает проверки и утверждения владельцем; код следующих релизов до утверждения не изменяется.

## 0. Утверждение плана и execution gates

Архитектурный план утверждается владельцем отдельно от разрешений на выполнение
конкретных релизов. Утверждение документа разрешает подготовку следующего gate, но само
по себе не разрешает менять production, мигрировать данные или сливать код.

Execution gates:

| Релиз | Что владелец подтверждает непосредственно перед выполнением |
|---|---|
| `0.11-STOP` | разрешение, точное окно, ответственный оператор и способ kill switch |
| `0.11R` | стратегия веток/PR и GitHub username независимого reviewer |
| `0.11A` | SLA reconciliation для delivery `unknown` |
| `0.11B` | канонические финансовые коэффициенты при уже утверждённой формуле |
| `0.11M` | окно миграции, retention, место export и допустимая точка необратимости |
| `0.11D` | production cutover и rollback decision |

Отсутствие решения для позднего релиза не блокирует более ранний gate. До отдельного
execution approval соответствующего релиза production не изменяется. PR #1 остаётся
Draft до завершения repository gate и независимой проверки.

## 1. Цель MVP

Создать Telegram-бота, который регулярно получает объявления о продаже автомобилей с фиксированной ценой, сохраняет историю изменений, сравнивает автомобиль с актуальными аналогами и отправляет пользователю объяснимое решение:

- `CONTACT` — связаться с продавцом;
- `WATCH` — наблюдать за ценой;
- `INSPECT` — требуется проверка автомобиля;
- `REJECT` — предложение не соответствует заданным параметрам.

Для каждого решения бот показывает цену объявления, рыночный диапазон, максимальную цену покупки, расходы, ожидаемую прибыль, ROI, риски, уверенность и использованные аналоги.

Первый пользовательский интерфейс — обычный Telegram-бот. TMA создаётся только после рабочего пилота и использует тот же backend API.

## 2. Границы проекта

В MVP входят только автомобили с фиксированной ценой в ОАЭ.

Не входят:

- недвижимость;
- аукционы, ставки, таймеры и отслеживание торгов;
- автоматическая покупка автомобиля;
- автоматическая отправка сообщений продавцам;
- прогноз цены без подтверждающих рыночных данных;
- TMA до завершения пилота Telegram-бота.

Для внешнего источника учитываются только технические параметры интеграции: формат данных, авторизация, лимиты, частота обновления, стабильность схемы, мониторинг и стоимость обработки.

## 3. Подтверждённое текущее состояние

На 24.07.2026 существуют три разные точки состояния, которые нельзя называть одним baseline:

| Контур | Фактическое состояние |
|---|---|
| default-ветка `main` | legacy: `DubizzleMockScraper`, SQLite, `GEMINI_API_KEY`, LLM-оценка рынка и бесконечный локальный цикл |
| draft PR #1 / рабочая ветка | крупный монолитный PR с кодом, Terraform и документацией; динамические counts намеренно не фиксируются, CI проходит, но критические дефекты целостности и доступа ещё не устранены |
| Google Cloud production | развёрнут образ из рабочей ветки, а не из слитой и воспроизводимой default-ветки; фактический код production необходимо связать с commit SHA и image digest |

Следовательно, ни `main`, ни draft PR #1 пока не считаются утверждённым production-baseline. До новых продуктовых функций требуется стабилизация, разделение изменений на проверяемые PR и синхронизация `main` с реально развёрнутой версией.

| Область | Сейчас | Целевое состояние |
|---|---|---|
| Источник кода | production развёрнут из неслитой рабочей ветки; `main` остаётся legacy | защищённая `main` однозначно воспроизводит развёрнутый release |
| Запуск | четыре Cloud Run collector Jobs и Cloud Scheduler из draft-ветки | сохранить отдельные расписания и добавить управляемые content/publisher jobs |
| Данные | реальные DubiCars, CarSwitch, Cars24 и OpenSooq; raw и версии | расширять источники после контроля качества |
| Хранилище | Firestore и Cloud Storage; SQLite только локально | добавить поисковые запросы, публикации и audit log |
| Оценка | Engine `2.3.0` есть в draft-ветке, но расходы, риски, аналоги и provenance требуют исправления | экономически проверенный и версионированный расчёт с точным snapshot и market context |

Рабочая ветка является аварийно развёрнутым кандидатом baseline, но не утверждённым источником production-кода. После утверждения плана последовательно выполняются отдельно разрешённый `0.11-STOP`, repository gate `0.11R`, стабилизация `0.11A–0.11C`, миграция `0.11M`, baseline `0.11D` и официальный пилот `0.11P`; только после их приёмки начинаются продуктовые релизы `0.12+`.

## 4. Принципы реализации

1. Одинаковые входные данные всегда дают одинаковое финансовое решение.
2. LLM не определяет рыночную цену, стоимость ремонта, прибыль, ROI или итоговое действие.
3. Неизменившаяся версия объявления не обрабатывается повторно и не вызывает Vertex AI.
4. Ошибка источника не подменяется mock-данными.
5. Сырые данные сохраняются до нормализации; каждое производное значение содержит provenance.
6. Backend не зависит от Telegram. Бот и будущая TMA являются клиентами Application API.
7. Каждый этап заканчивается работающим вертикальным результатом и автоматической проверкой.
8. Новые источники подключаются адаптерами, не меняющими расчётное ядро.
9. Решение всегда рассчитывается по точному `listing_id + content_hash`; подмена переданной версии последним snapshot запрещена.
10. Пользовательские данные всегда фильтруются по владельцу на уровне запроса и проверяются integration-тестами.
11. Временная ошибка внешнего сервиса приводит к контролируемому retry, а постоянная невалидность данных — к карантину.
12. Для внешней доставки не заявляется недостижимое «ровно один раз»: используется outbox, детерминированная идентичность, состояние неоднозначной доставки и запрет слепого повтора.
13. `main`, release image digest и фактически развёрнутая Cloud Run revision должны однозначно соответствовать друг другу.
14. Все составные идентификаторы строятся из версионированного canonical JSON и SHA-256, а не конкатенацией строк.

## 5. Целевая схема

```text
Cloud Scheduler
    -> Cloud Run Job: collector-{source}
    -> Cloud Storage: raw snapshot
    -> Firestore: listing + snapshot metadata
    -> Cloud Tasks: process-listing
    -> Cloud Run API/worker
       -> normalize
       -> entity resolution
       -> comparable pricing
       -> cost and risk
       -> decision
       -> optional Vertex AI enrichment
       -> Firestore: decision
       -> Cloud Tasks: Telegram delivery
       -> Telegram Bot API

Telegram webhook -> Cloud Run API -> Firestore
Firebase Hosting: Admin -> Firebase Auth -> Cloud Run Admin API
PublicationEvent -> Telegram Free adapter
                 -> Telegram Pro adapter
                 -> Telegram personal adapter
                 -> WhatsApp Business adapter (только после настройки)
TMA после пилота -> Firebase Hosting/Auth -> тот же Cloud Run API
```

### Релиз 0.7. Cost, Risk и Decision Engines

Задачи:

- рассчитать проверку, регистрацию/transfer fee, ремонт, подготовку, хранение, стоимость капитала, расходы на продажу и резерв риска;
- поддержать точечные значения и диапазоны расходов;
- определить hard stop flags и предупреждения;
- рассчитывать консервативную цену перепродажи;
- рассчитывать максимальную цену покупки, прибыль и ROI;
- вернуть `CONTACT`, `WATCH`, `INSPECT`, `REJECT` или `INSUFFICIENT_DATA`;
- версионировать правила и конфигурацию решения;
- добавить regression tests для всех fixture-сценариев.

Основные формулы:

```text
R = market_low × (1 - liquidity_discount_rate)
repair_basis = repair_high
c = annual_capital_rate × hold_days / 365
r = risk_rate
base_fixed = inspection + registration + repair_basis + preparation + holding
selling = R × selling_rate
capital(P) = (P + inspection + registration + repair_basis + preparation) × c
risk_reserve(P) = (P + repair_basis) × r
non_purchase_cost(P) = base_fixed + selling + capital(P) + risk_reserve(P)
expected_profit = R - asking - non_purchase_cost(asking)
roi_percent = expected_profit / (asking + non_purchase_cost(asking)) × 100
constant = base_fixed + selling
           + c × (inspection + registration + repair_basis + preparation)
           + r × repair_basis
max_purchase_price = (R - target_profit - constant) / (1 + c + r)
```

Все rate-поля (`liquidity_discount_rate`, `selling_rate`, `annual_capital_rate`, `risk_rate`) хранятся как Decimal-доли `0..1`, а проценты используются только в представлении. Денежные входы сериализуются десятичными строками AED; двоичный float запрещён. Промежуточные вычисления сохраняют не менее четырёх знаков AED, итоговые денежные поля округляются `ROUND_HALF_UP` до `0.01 AED`, а допустимая цена покупки консервативно округляется вниз до целого AED. Если необрезанный `max_purchase_price <= 0`, значение для предложения равно `0 AED`, а действие не может быть `CONTACT/INSPECT`.

Резерв риска не вычитается второй раз: он уже входит в `non_purchase_cost`. Selling cost считается от `R`, capital cost — от вложений до продажи. Диапазоны ремонта и прочих неопределённых расходов сохраняются, а применённая консервативная граница, единицы rate и rounding policy входят в объяснение решения и `financial_config_version`.

Критерий приёмки:

- арифметика и округление покрыты unit-тестами;
- правила не зависят от LLM;
- решение объясняет каждый вычет и stop flag;
- отсутствие обязательных данных снижает confidence либо останавливает решение.

ID contract фиксирует: Unicode NFC и отсутствие whitespace; лексикографическую сортировку ключей; сортировку массивов-множеств по schema key; сохранение явно значимого порядка; money Decimal как строку с двумя знаками, rate как строку с шестью знаками без exponent; UTC RFC 3339 timestamps с миллисекундами; различие null и отсутствующего поля; lowercase SHA-256 hex из 64 символов. - проверять rollback только с учётом schema compatibility и migration checkpoint из `0.11M`;
- синхронизировать README и `.env.example` с командами чистого checkout.

Критерий приёмки:

- `main` больше не запускает mock/SQLite/Gemini legacy pipeline по умолчанию;
- clone `main` воспроизводит тесты, контейнер и описанную архитектуру;
- `/version`, Cloud Run revision и Git commit однозначно связаны;
- production использует image digest из прошедшего staging release;
- PR #1 не остаётся единственным непроверяемым пакетом всех подсистем.

### Релиз 0.11P. Официальный пилот и калибровка

Статус: выполняется только после migration reconciliation `0.11M` и приёмки baseline `0.11D`.

Все pilot/backfill результаты до этого gate считаются диагностическими и не входят в официальную оценку precision, ошибки цены и конверсии.

Объём пилота: не менее 100–300 обработанных объявлений и ручная проверка всех отправленных кандидатов.

Измерять:

- precision уведомлений `CONTACT/INSPECT`;
- долю `INSUFFICIENT_DATA`;
- ошибку рыночной оценки на доступном ground truth;
- долю дублей после entity resolution;
- задержку от появления объявления до уведомления;
- число повторных уведомлений;
- долю ошибок collector и parsing;
- стоимость обработки объявления и месячную стоимость облака;
- переходы `уведомление -> контакт -> осмотр -> покупка -> продажа`.

Критерий приёмки:

- пороги KPI утверждены до начала пилота;
- каждый ложный сигнал относится к конкретной причине;
- коэффициенты изменяются только версионированной конфигурацией;
- решение о переходе к `0.12+` и TMA принимается по итогам пилота, а не по готовности интерфейса.

Только после приёмки `0.11P` разрешается начинать следующий релиз.

### Релиз 0.12. Разделение Free и Pro

Цель: превратить публичный канал в витрину, а закрытый Pro — в платный информационный продукт.

Задачи:

- ввести общий `PublicationEvent`, отдельные форматы `PublicTeaser` и `ProDealCard` и использовать generic outbox из `0.11A`;
- публично показывать только марку, модель, год, защищённое изображение и CTA;
- не использовать оригинальную фотографию без обработки: применять crop/blur/watermark либо нейтральное изображение модели и при необходимости задержку тизера;
- скрыть в Free прямую ссылку продавца, listing ID, точную прибыль, ROI, максимальную цену покупки, полный рынок и аналоги;
- в Pro сохранить полную проверенную карточку;
- включить в Pro максимальную цену покупки, детализацию расходов, risk flags, причины решения, размер и состав аналогов, версию Engine и дату рыночного среза;
- создавать отдельный notification ID на каждый target и формат;
- хранить Telegram `message_id`, формат и версию шаблона для последующего редактирования или удаления;
- добавить предпросмотр обоих форматов на fixture и production-кандидате;
- подготовить одноразовую инструкцию очистки старых полных сообщений публичного канала: Bot API не умеет перечислять историю, поэтому сообщения без сохранённых `message_id` удаляются владельцем вручную.

Критерий приёмки:

- один кандидат создаёт короткий Free-тизер и отдельную полную Pro-карточку;
- в Free отсутствуют прямые идентификаторы; остаточная discoverability через внешний поиск признаётся и измеряется, а не объявляется абсолютно невозможной;
- ошибочный или неподтверждённый кандидат не появляется ни в одном канале;
- повтор задачи не дублирует ни Free, ни Pro;
- владелец утверждает тексты и внешний вид обоих форматов до production-развёртывания.

### Релиз 0.13. Подбор машины по запросу

Цель: пользователь формулирует потребность в личном чате, получает текущие варианты и подписку на новые совпадения.

Задачи:

- открыть `/start`, `/find`, `/my_searches` и `/stop_search` обычным пользователям;
- оставить `/sources`, ручной scan и системные настройки только администраторам;
- поддержать русский и английский запрос вида `Toyota Prado 2020+, GCC, до 180000 AED, до 100000 км`;
- преобразовывать текст в `SearchRequest` с маркой, моделью, годом, бюджетом, пробегом, specification и инвестиционными порогами;
- показывать распознанные параметры и требовать подтверждение до сохранения;
- не додумывать отсутствующие параметры; LLM при наличии используется только для извлечения структуры;
- искать по последним нормализованным объявлениям и повторно проверять цену каждого результата;
- переиспользовать owner-scoped фильтры `/deals` и push, уже исправленные в `0.11A`;
- при отсутствии результата сохранять активную подписку и проверять её при каждом новом решении;
- ограничить объём бесплатной выдачи и частоту запросов конфигурацией тарифа.

Критерий приёмки:

- тестовые русские и английские запросы преобразуются в ожидаемые фильтры;
- результат удовлетворяет всем подтверждённым ограничениям пользователя;
- `/deals` не возвращает автомобили вне бюджета, марок, минимальной прибыли и ROI пользователя;
- `Price on request`, устаревшая цена и неподтверждённый listing исключаются;
- отсутствие совпадений создаёт подписку, а новое совпадение доставляется один раз;
- административные команды недоступны обычному пользователю.

### Релиз 0.14. Панель управления

Цель: управлять работающим продуктом без терминала, ручного редактирования `.env` и Google Cloud Console для повседневных операций.

Архитектура:

```text
Firebase Hosting: admin frontend
    -> Firebase Authentication: Google sign-in
    -> Cloud Run Admin API: проверка Firebase ID token и роли admin
    -> Firestore / Cloud Run Jobs / Cloud Tasks
```

Первая версия панели:

- dashboard источников, свежести данных, очередей и ошибок;
- включение/отключение и ручной запуск только зарегистрированных адаптеров;
- просмотр последних решений, detail-page verification и карантина;
- просмотр Free/Pro preview и истории доставки;
- управление версионированными порогами прибыли, ROI и качества;
- управление расписанием и режимом информационного контента;
- просмотр пользователей, запросов и подписок;
- журнал действий администратора.

Ограничения:

- секреты не читаются и не изменяются из панели;
- изменение источника не добавляет произвольный scraper: новый адаптер по-прежнему требует код и contract tests;
- опасные действия требуют явного подтверждения и записываются в `admin_audit`;
- панель администратора не является TMA и не меняет последовательность пользовательского продукта.

Критерий приёмки:

- неавторизованный запрос получает `401/403`;
- разрешённый Firebase UID видит dashboard и может включить, отключить и запустить источник;
- изменение порога создаёт новую версию конфигурации и audit event;
- ни один API-ответ панели не содержит секретов;
- frontend и API проходят E2E smoke test в production.

### Релиз 0.15. Информационный модуль

Цель: поддерживать регулярный интерес аудитории между редкими сильными сделками.

Рубрики первой версии:

- ежедневный `Market Pulse`: объём новых объявлений, медианные диапазоны и число снижений цены;
- `Price Drop`: крупнейшие подтверждённые снижения;
- недельный обзор популярных моделей и ценовых диапазонов;
- разбор подтверждённого предложения с объяснением факторов;
- Telegram poll и CTA к `/find` и Pro.

Задачи:

- рассчитывать факты только из Firestore за явно указанный период;
- указывать размер выборки и дату среза;
- запрещать публикацию при недостаточной выборке или проваленной data-quality проверке;
- хранить `ContentPost`, источники фактов, статус `draft/approved/published` и шаблон;
- разрешить полностью автоматический режим только для утверждённых детерминированных шаблонов;
- использовать Vertex AI исключительно для переформулирования уже рассчитанных фактов;
- настраивать рубрики, частоту, Free/Pro target и режим согласования через панель.

Критерий приёмки:

- публикация содержит период и размер выборки;
- LLM не может изменить числовые значения;
- повтор job не создаёт второй пост за тот же период и рубрику;

## 7. Сквозные требования

### Надёжность

- все сетевые операции имеют timeout;
- повторяются только временные ошибки;
- задачи идемпотентны;
- предусмотрены dead-letter состояния;
- graceful shutdown обязателен для Service и Jobs;
- недоступность одного источника не останавливает pipeline.

### Данные

- Firestore хранит оперативные и индексируемые данные;
- Cloud Storage хранит raw snapshots;
- SQLite не используется в production;
- URL не является единственным идентификатором;
- история цены и состояния объявления не перезаписывается;
- все timestamps хранятся в UTC.

### Секреты и доступ

- секреты не находятся в Git, Docker image или обычных переменных CI;
- production использует Secret Manager и service accounts;
- IAM выдаётся отдельно API, collectors, Tasks и CI;
- Telegram MVP ограничен allowlist пользователей;
- логи не содержат токены, телефоны и полный текст секретов.

### Тестирование

- unit tests — модели, формулы, нормализация и правила;
- contract tests — адаптеры на сохранённых raw snapshots;
- integration tests — Firestore emulator и API;
- end-to-end smoke test — collector fixture -> decision -> тестовая Telegram-доставка;
- regression tests — контрольный датасет;
- load test — обработка пачки объявлений и очередь уведомлений.

### Наблюдаемость и стоимость

- единый correlation ID проходит через collector, task, decision и notification;
- логи структурированы;
- определены метрики свежести, ошибок, задержки, дублей и стоимости;
- настроены алерты на отсутствие успешного сбора, рост ошибок и backlog очереди;
- настроены бюджеты и лимиты Vertex AI.

## 8. Порядок выполнения ближайших работ

Переход к полной реализации подтверждён владельцем проекта. Релизы выполняются в следующем порядке:

1. получить от владельца правки и явное утверждение этой редакции плана;
2. после отдельного подтверждения выполнить `0.11-STOP` и ограничить production;
3. выполнить `0.11R`: создать issues, защитить `main`, определить replacement PR strategy и reviewer;
4. выполнить `0.11A`: точные версии, изоляция пользователей, роли, retry и outbox;
5. выполнить `0.11B`: достоверность цен, аналогов, decision identity, рисков и финансовой модели;
6. выполнить `0.11C`: lifecycle, масштабирование, конфигурация, IaC и воспроизводимая сборка;
7. выполнить `0.11M`: watermark, test restore, миграцию схемы, raw replay и reconciliation;
8. выполнить `0.11D`: слить принятые replacement PR в `main` и развернуть прошедший staging image digest;
9. выполнить официальный пилот `0.11P` на воспроизводимом baseline;
10. выпустить разделение `Free teaser / Pro full card`;
11. выпустить пользовательский `/find` и подписки на новые совпадения;
12. выпустить административную панель на Firebase Hosting/Auth;
13. выпустить информационный модуль в режиме предварительного согласования;
14. перейти к автоматическим информационным публикациям после ручной проверки шаблонов;
15. подключить официальный WhatsApp Business adapter после предоставления Meta-реквизитов;
16. провести контрольный запуск монетизации и только затем возвращаться к TMA.

Каждый релиз выполняется отдельным pull request либо небольшой серией pull request. Следующий релиз не начинается, пока не выполнены критерии приёмки предыдущего или письменно не зафиксировано исключение.
