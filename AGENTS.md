# Правила разработки (AGENTS.md)

Для всех агентов, работающих с проектом **Dubai Deal Sniper**, действуют следующие строгие правила:

1. **Язык общения и документации:** Все комментарии, документация (включая коммиты и логи) и общение с пользователем ведутся строго на русском языке.
2. **Среда разработки:** Windows 11 PowerShell. Учитывать синтаксис PowerShell при работе с консолью (например, использование правильных разделителей путей, кавычек и т.д.).
3. **Чистый Python:** Код пишется под Python 3.11 с обязательным использованием type hints (аннотаций типов).
4. **Безопасность конфигурации:** Категорически запрещено коммитить или хардкодить любые API-ключи, токены или личные данные. Все параметры должны считываться из `.env`.
5. **Предотвращение дублирования:** Запросы к Gemini API должны выполняться только для новых объявлений, которые еще не были сохранены в локальной SQLite базе данных.
6. **Обновление документации:** После каждого успешно завершенного шага обязательно обновлять `docs/STEPS.md` и `AI_CONTEXT.md`.
7. **Обязательный анализ перед исправлением:** Перед каждым изменением кода агент заново проверяет относящиеся к задаче требования `SPEC.md`, утверждённый план, архитектуру, операционный регламент, фактический код, тесты и доступное production evidence. Исправление отдельного симптома без проверки сквозного контура запрещено.
8. **Документы и утверждение до кода:** Сначала агент документирует диагноз, границы изменения, зависимости, риски, миграцию, тесты и релизный порядок. Код разрешён только после явного утверждения этого плана владельцем. Deploy разрешён только после локального gate, immutable build, требуемого staging rehearsal и отдельного подтверждения владельца.
9. **Сквозной gate и запрет частичных микрорелизов:** До начала реализации агент обязан составить и поддерживать единую матрицу `требование → источник → raw/detail/photo evidence → нормализация/identity → аналоги → решение → publication/outbox/delivery → канал/бот/TMA/Admin → пользовательский результат → мониторинг`. Для каждого затронутого звена фиксируются код, автоматический тест, staging evidence и ожидаемый production evidence. Дефект нельзя считать закрытым, если проверен только видимый симптом, если хотя бы одно затронутое звено не проверено либо если исправление требует несовместимого «следующего микроплана». Новый симптом во время реализации останавливает release, дополняет единый утверждённый план и повторно проходит весь сквозной gate; изменение границ, архитектуры или риска требует нового утверждения владельца.
